# FLUX.2 dev generation

Accepted November 10, 2026 for the administrator preview.

Image generation uses a dedicated authenticated backend, separate from Qwen chat and image understanding. The Next.js server verifies the Google account and active session, applies the existing administrator allowlist, and supplies the verified account UUID with a server-only backend credential. Browser headers and body fields never establish backend identity. The backend enforces ownership, one active generation, daily starts and temporary-result retention.

The browser stores image PNG bytes in IndexedDB using account-and-message keys. Cloud conversation history stores only a versioned whitelist of prompt, request ID, job ID, state and cancellation request flag. Browser-only bytes avoid adding permanent object storage in the first release. An account-scoped local origin marker is persisted before submission and is excluded from cloud history. Only the originating browser may resume or retrieve the same job; other browsers retain a placeholder and prompt and may explicitly generate a new request. If origin persistence fails, submission is blocked before GPU work starts. Downloading is the durable user-controlled export. Clearing site data removes local images; deleting cloud history does not remove exported files or disconnected browser copies.

Submissions use a stable idempotency key within the lifetime of the backend process. Unknown submission outcomes without a job ID are never automatically re-POSTed after reload: only a new explicit Generate action or manual check may submit. The manual check explains that a restarted backend may accept another generation because its idempotency record was lost. Automatic reload recovery only polls known job IDs. Completed backend status and successful local image saving are distinct: the card shows an actual preview and local-save notice only after reading a stored PNG. Downloads pass through authenticated same-origin routes with bounded response reads, fixed PNG header/dimension checks, and no public URLs in history. Failed saves remain recoverable from the same temporary job.

Cancellation is cooperative. The UI distinguishes a requested cancellation from confirmed cancellation and permits completion to win after backend artifact persistence. Deleting a conversation requests cancellation of known unfinished jobs and aborts local image work before deleting its blobs. Backend TTL controls abandoned or unknown jobs.

The UI offers separate Chat and Create image modes. Only an explicit text prompt goes to FLUX; Qwen attachments and conversation context are excluded. This release uses one 1024 × 1024 PNG, 28 steps, guidance 4, twenty account starts per day and a 24-hour maximum terminal-result TTL. At the user's request there is no waiting queue or SQLite database: additional requests receive busy responses, and temporary status, idempotency and usage records reset on service restart. Known job IDs from a previous service process become unavailable rather than being silently regenerated. An additive SQL migration extends the existing cloud history whitelist; rollout must apply it before frontend activation, after the web-search metadata migration that installs `public.clean_web_search_metadata(jsonb)`. A transactional preflight rejects a missing prerequisite before replacing the existing history cleaner.


## Reference editing extension

Reference editing reuses the existing job API and account/origin boundaries. A saved local output is the only selectable source; it is decoded and normalized to RGB JPEG in memory. The instruction and one reference are submitted together, with backend `kind: edit` acknowledgement required. The image composer and Qwen attachment draft remain separate; removing the reference is an explicit user action.

An additive migration persists only `mode: edit` and the source **message ID** (`sourceImageId`), matching the account-scoped IndexedDB key. Invalid/missing provenance retains edit intent, so unavailable sources cannot silently turn into text-only requests. No normalized reference bytes are synced or persisted. Only the most recent ambiguous edit retains its exact normalized bytes until a job is known, bounding retry memory; unknown submissions after reload require a fresh explicit edit from the saved source. This avoids both automatic duplicate work after backend restarts and prompt-only fallback.

Reference edits use metadata version 2. Existing version-1 parsers reject that shape instead of stripping edit intent. Because older cloud loaders render raw RPC messages before parsing, the new client reads a versioned RPC; the legacy read rejects any page containing version-2 image metadata. Both paths retain the same session, ownership and pagination checks. Rejection avoids the metadata erasure that masking would permit during an older client save. Backend capability and job API versions remain unchanged.

The write boundary is versioned too: an older tab may restore a current revision from the shared browser cache without performing a read. The legacy saver therefore locks the same account row as the original saver and rejects existing version-2 histories with a conflict. New clients call a copied `save_chat_v2` with the original body unchanged. Holding the account lock across the legacy check and delegation closes the race with a concurrent edit save; revision checks continue to protect stale copies.
