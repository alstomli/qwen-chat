# Web search

Every eligible normal text request automatically enables the existing model tool loop. There is no composer toggle or retry flag dependency: the model decides whether to search, answer directly, or clarify from the natural-language request and conversation. Current prices and explicit verification requests need web evidence; stable explanations and supplied-text tasks normally answer directly. Explicit requests not to browse are honored by the model's policy. Relevant queries may be sent to the configured search provider; the composer discloses this.

The authenticated `/api/chat` route authoritatively selects `webSearch: {version: 1, mode: "auto"}` after checking the model/adapter capability. Unsupported profiles and image messages retain the plain path, with a visible unavailable notice. An enabled run fails closed if the gateway does not confirm `X-Chat-Web-Search: 1`. BF16 still requires an exact base/adapter profile capability. Auth, quotas, adapter confirmation, image handling, and legacy history remain in force. No provider key is configured in browser or public variables. The gateway retains its version-one `off`, `auto`, and `required` contract for other clients.

Version-one SSE `web-status`, `web-sources`, and `web-complete` events have one run ID and increasing sequence numbers. Sources are cumulative and IDs cannot be rebound to a different URL. Both the server proxy and browser validate the metadata. Registered `[S1]` markers and source URLs become links scoped to that message; unregistered links in a web answer are rendered as text. Direct runs with no sources keep ordinary answer links and show no search-success label. Code blocks remain unchanged. The sources list distinguishes search snippets from pages actually read and records retrieval time. A failed, stopped, or interrupted run retains that state and does not show a successful web-answer label.

The proxy's web deadline is the lesser of 240 seconds and the effective request timeout, measured from route entry, below the route's 300-second limit. Stop cancels the stream and upstream request. Backend search, page-reading and model-call budgets apply within that deadline. Unsupported plain requests retain their existing timeout behavior. Eligible direct answers share the tool-loop deadline and planner/final overhead.

## Rollout

1. Apply `supabase/migrations/202611100001_web_search_metadata.sql` after the two existing migrations. This replaces the existing payload cleaner additively and adds a private metadata cleaner; it preserves history RPCs, ownership controls and old docs metadata.
2. Deploy the companion inference gateway update, configure its server-side search provider key, and enable only model/adapter aliases whose native tool calling has been verified. Provider enablement and real-model verification are separate operational steps.
3. Deploy this frontend after the gateway and database changes. It needs no search provider credentials or additional public environment variables. Until an alias advertises verified availability, the composer shows an unavailable explanation and text chat uses the plain path.

Browser storage, cloud history and JSON/Markdown exports retain only bounded citation metadata: version, run ID, terminal outcome, and up to ten source IDs, titles, URLs, retrieval times and evidence kinds. No raw pages, snippets, tool arguments, provider keys or tool traces are saved. Legacy `searchRequested` history remains readable but does not control retries. Follow-up model messages remain the existing text-only history; source registries are not concatenated into prompts or rebound across turns.

Local validation uses unit and route fixtures, a production build, and local PostgreSQL migration checks. These checks do not provision a search provider, apply hosted migrations, deploy services, or prove native tool calling on the live BF16 model. Those operational checks remain necessary before enabling a live profile.
