# FLUX image generation and reference editing

Configure the dedicated backend's HTTPS origin in `FLUX_IMAGE_API_URL` and its shared server credential in `FLUX_IMAGE_API_KEY`. These values are server-only. Apply migrations in order before enabling the frontend. In particular, `supabase/migrations/202611100001_web_search_metadata.sql` must already provide `public.clean_web_search_metadata(jsonb)` before applying `supabase/migrations/202611110001_generated_images.sql`. The image migration fails transactionally with a clear prerequisite error if that helper is missing, preserving the previous history cleaner. The backend must implement capability contract version 1 and authenticate all job access by its API credential plus the server-verified `X-Chat-User-Id`; inbound browser identities are never forwarded.

The existing advanced-settings administrator allowlist gates every image route and the Create image composer. Chat attachments continue to use Qwen image understanding. Text-to-image requests use a prompt and request one 1024 × 1024 PNG with backend defaults of 28 steps and guidance 4. The backend accepts one generation at a time with no waiting queue; additional submissions receive a busy response. Temporary status, idempotency records, and twenty-starts-per-account/day counters are held in memory and reset when the service restarts. Results expire after 24 hours at most and can become unavailable sooner after a container replacement.

Image bytes are saved in IndexedDB under account-and-message keys. Prompts, request IDs, job IDs and states sync as compact cloud history metadata. Downloads use authenticated `/api/images/{jobId}/image` requests; no public asset URL is stored. A separate account-scoped browser marker is saved before submission and never included in cloud history. Only that originating browser resumes polling or image retrieval for known job IDs after reload. An unconfirmed submission without a job ID is never automatically submitted again; its outcome remains unknown until an explicit user check. Because backend idempotency resets on restart, that manual check can create another generation after a restart. Other browsers display a metadata placeholder and can explicitly generate a new image. If the browser cannot persist its origin marker, generation does not start. Download important results: clearing browser data removes local images, and text history exports do not include image files. History deletion removes this browser's matching blobs and requests cancellation of unfinished known jobs; copies downloaded or retained on another browser are unaffected.

Submission IDs remain stable for explicit retries, but backend idempotency survives only while its process survives. Only explicit Generate or a manual check can POST; automatic reload recovery only reads known job IDs. Cancellation is cooperative; completion may win if an image has already been persisted. Backend status and result retention remain authoritative. The proxy permits HTTPS in production, bounds JSON and image bodies, validates fixed-size PNG headers, and returns allowlisted metadata and errors.


## Edit a saved generated image

Administrator accounts can choose **Edit this image** on a generated image saved in this browser after the backend confirms reference-edit readiness. The composer loads the actual account-scoped IndexedDB image, prepares a 1024 × 1024 RGB JPEG (at most 2 MiB), and shows a removable reference preview. Enter a new instruction and explicitly apply the edit. Chat attachment drafts are separate and continue using Qwen image understanding. This flow does not accept external URLs or upload arbitrary files.

The API accepts one optional `referenceImage` PNG/JPEG data URL. It authenticates the account before reading a bounded request, decodes the image with Sharp, and verifies format, one frame and exact 1024 × 1024 dimensions before forwarding. A reference may contain at most 3 MiB decoded image bytes; the entire JSON body is limited to 4 MiB + 16 KiB. Backend capability `referenceEditing: true` and a matching enabled version-1 `imageEditing` capability are required. The backend must acknowledge `kind: edit`; otherwise the client fails closed.

Apply `supabase/migrations/202611110002_reference_image_metadata.sql` after the earlier image-history migration. Reference edits use metadata version 2, while existing text-to-image metadata remains version 1. Only `mode: edit` and `sourceImageId` (the source message ID used as the account-scoped IndexedDB key) are added to cloud history and exports. Reference bytes and normalized upload data URLs stay in memory and never enter cloud history, localStorage, logs or exports. The existing source PNG remains in this browser's IndexedDB. **Edit again** reopens that original saved source and instruction for a new explicit submission; missing source bytes never become a text-only generation. **Remove reference** explicitly changes the composer back to text-to-image.

Known edit job IDs may resume status retrieval after reload only in their originating browser. Unknown edit submissions never automatically POST. Only the most recent ambiguous edit retains its normalized reference in memory. A same-request retry needs those exact bytes; after reload, start a new explicit edit from the saved source instead. The earlier request may already have been accepted. Process-local backend idempotency and busy admission remain authoritative.

Reference history compatibility requires `supabase/migrations/202611110003_versioned_image_history_reads.sql` before rollout. New clients read `get_chat_history_v2` with the existing account/session checks and pagination. The legacy read RPC rejects pages containing version-2 image metadata and asks the user to reload, preventing an older open app from interpreting edit instructions as text-only image prompts or overwriting edit intent. Existing cached writes remain protected by revision checks. Backend capability/API contract version remains 1.

Also apply `supabase/migrations/202611110004_versioned_image_history_writes.sql` before rollout. New clients write through `save_chat_v2`, copied from the deployed saver without changing its session, account lock, revision, idempotency or quota behavior. The legacy saver holds that same account lock and returns conflict for an owned conversation containing version-2 edit metadata, preventing an older open app from stripping edit intent from a shared browser cache even when it holds the latest revision. Other legacy text-only saves remain unchanged.
